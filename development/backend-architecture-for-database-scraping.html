How the source pipeline actually runs

Every legal/financial figure the product shows (Bildungsurlaub days, Homeoffice-Pauschale caps, Blue Card thresholds) comes from this pipeline into sources.json — never guessed, never hardcoded in the UI.

Scraping public legal content This pipeline

Collecting rules like “Bildungsurlaub in Hessen = 5 days, 6-month wait.” Static public information — RDG/StBerG regulate giving advice, not collecting public facts, so there's no legal exposure here.

Parsing user-uploaded documents Separate stack

Reading an uploaded payslip or contract isn't scraping — it's an OCR/Document-AI problem (Mindee, Affinda-style commercial APIs). Different stack, out of scope for this diagram.

Tools — verified status, not assumed
scrapling ✓ Installed

Default choice. Static pages, stealthy-fetch for bot-guarded sites, full-browser fetch for JS-heavy pages.

Playwright (MCP) ✓ Verified working

Anything needing real interaction — filling a questionnaire, clicking through a flow, confirming what a competitor's product shows.

WebSearch / WebFetch ✓ Built-in

Fast fact-finding without a known URL yet. What most legal/market research so far actually used.

firecrawl CLI ✗ Not installed

Would add site-wide map, schema agent extraction, and scheduled monitor — only worth setting up at scale.

The 5-stage pipeline
1 Discover WebSearch / scrapling Find candidate URLs against a known government portal.
→
2 Extract scrapling / Playwright Pull the actual text — static get, stealthy-fetch, or full browser as needed.
→
3 Verify cross-check ×2 Primary + secondary source. Disagreement → confidence: low, flag for review.
→
4 Store sources.json Merge in — update existing id or add new, method filled in honestly.
→
5 Monitor manual, for now No automated tool yet — next_check_due schedules re-verification by hand.
What lands in sources.json
{
  "id": "bildungsurlaub-hessen",
  "category": "Bildungsurlaub",
  "region": "Hessen",
  "law_short": "HBUG",
  "facts": { days_per_period, waiting_period_months, … },
  "source_primary": "gesetze-im-internet.de/…",
  "source_secondary": [ cross-check URLs ],
  "method": "websearch | scrapling | playwright | …",
  "confidence": "high | medium | low",
  "last_verified": "2026-09-10",
  "next_check_due": "2027-01-01"
}
source_primary is always the statute text or official statistic itself — never a blog or explainer. Those go in source_secondary, for cross-checking only.
method records which tool actually produced the entry, so nobody has to guess later whether a fact was scraped, searched, or manually confirmed.
confidence stays honest — e.g. Bildungsurlaub usage-rate stats couldn't be found anywhere, so that gap is marked low rather than silently omitted.
next_check_due exists because rates and caps change yearly — this is what schedules re-verification, not a one-time pull.
The DB is segmented by Consumer Journey step, not one flat table
SEG 1 Job Offer Check 🆕 Not started
SEG 2 Visa Researched, not in JSON
SEG 3 Accommodation Researched, not in JSON
SEG 4 Insurance Researched, not in JSON
SEG 5 Tax ✓ 12 entries live

A user on Step 5 pulls only from Seg 5 — the DB doesn't need to be complete everywhere at once, just current where it's used.
Run day-to-day with: "add these 3 new states to sources.json, following the existing schema, verify with scrapling/WebSearch" — a human reviews anything that comes back confidence: low.
